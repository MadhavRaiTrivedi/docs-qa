# Docs Q&A: Requirements

## 1. Problem statement

Teams keep their knowledge in PDFs and Markdown files: HR policies, runbooks, onboarding guides, product specs. Finding one answer means guessing the right file and searching it by keyword, which fails when the question uses different words from the document.

Docs Q&A lets a team upload its documents and ask questions in plain language. It retrieves the passages that answer the question, has an LLM write an answer from those passages only, and cites the file and page for every claim. When the documents do not contain the answer, it says so instead of guessing.

## 2. Actors

| Actor | Description |
|---|---|
| Reader | Asks questions in a collection and reads answers with their sources. Rates answers. |
| Editor | Creates collections, uploads, replaces and deletes documents. |
| System | Background ingestion worker: parses, chunks and embeds uploaded documents. |

## 3. Core concepts

- **Collection**: a named set of documents that are searched together, for example "HR policies". A question is always asked inside one collection.
- **Document**: one uploaded file. It goes through ingestion before it can be searched.
- **Chunk**: a passage of a document, a few hundred tokens long, with its position (page or heading) in the source file. Chunks are the unit of retrieval and of citation.
- **Embedding**: a vector produced by the embedding model for a chunk or a question. Similar meaning gives nearby vectors.
- **Retrieval**: finding the chunks most relevant to a question, by combining vector similarity and keyword search.
- **Answer**: text generated by the LLM from the retrieved chunks, with citations pointing back to those chunks.

## 4. Functional requirements

Priority uses MoSCoW: **M**ust, **S**hould, **C**ould.

### Collections and documents

| ID | Requirement | Priority |
|---|---|---|
| FR-01 | An editor can create, rename and delete a collection. Deleting a collection deletes its documents and chunks. | M |
| FR-02 | An editor can upload a PDF, Markdown or plain text file to a collection, up to a configured size limit. Other formats are rejected. | M |
| FR-03 | Upload returns immediately. Ingestion runs in the background and the document's status shows its progress. | M |
| FR-04 | A document has a status: `Uploaded`, `Processing`, `Ready` or `Failed`. A failed document records the reason and can be retried. | M |
| FR-05 | Uploading a file whose content is identical to a document already in the collection returns the existing document instead of ingesting it twice. | S |
| FR-06 | An editor can replace a document with a new version. Old chunks stay searchable until the new version is `Ready`, then are removed in one step. | S |
| FR-07 | An editor can delete a document. Its chunks are no longer returned by any search. | M |
| FR-08 | A user can list a collection's documents with status, page count and chunk count. | M |

### Asking questions

| ID | Requirement | Priority |
|---|---|---|
| FR-09 | A reader can ask a question in a collection and receive an answer generated only from that collection's documents. | M |
| FR-10 | Every answer lists its sources: document name, page or heading, and the passage. Each claim in the answer carries a `[n]` marker that links to the source supporting it. | M |
| FR-11 | If no retrieved chunk is relevant enough, the service answers that the documents do not cover the question, without calling the LLM. | M |
| FR-12 | Retrieval combines vector similarity and full-text keyword search, merged with Reciprocal Rank Fusion. | M |
| FR-13 | The answer streams to the client token by token (Server-Sent Events). | S |
| FR-14 | A reader can ask follow-up questions in a conversation. The follow-up is rewritten into a standalone question before retrieval. | C |
| FR-15 | Retrieved chunks are reranked by a cross-encoder before being sent to the LLM. | C |

### Feedback and evaluation

| ID | Requirement | Priority |
|---|---|---|
| FR-16 | A reader can rate an answer as helpful or not helpful, with an optional comment. | S |
| FR-17 | An evaluation command runs a set of questions with known answers and source passages against a collection and reports retrieval hit rate, MRR and answer faithfulness. | M |
| FR-18 | Every question records the retrieved chunks, the model used, token usage and latency, so a bad answer can be traced to bad retrieval or bad generation. | M |
| FR-19 | A web UI to manage collections, upload documents, and ask questions with clickable sources. | S |

## 5. Non-functional requirements

| ID | Requirement |
|---|---|
| NFR-01 | **Grounded answers**: the LLM is instructed to answer only from the supplied passages and to cite them. An answer with no citation is shown as unsupported. |
| NFR-02 | **Prompt injection**: document text is passed to the LLM as escaped, numbered `<source>` blocks in the input, never merged into the instructions. The instructions tell the model to ignore instructions found inside sources. |
| NFR-03 | **Ingestion reliability**: a worker crash during ingestion never leaves a document half-indexed. Chunks of a document are written in one transaction, and a job stuck in `Processing` past a timeout is picked up again. |
| NFR-04 | **Embedding model consistency**: each chunk records the embedding model that produced it. Questions are embedded with the same model. Changing the model requires re-ingestion and is never mixed silently. |
| NFR-05 | **Performance target**: retrieval p95 under 150 ms on a collection of 50,000 chunks, and time to first answer token p95 under 3 s, measured with a load test on a single developer machine. |
| NFR-06 | **Answer quality target**: retrieval hit rate@6 of at least 0.85 on the evaluation set, measured with the evaluation command before any change to chunking or retrieval is merged. |
| NFR-07 | **Cost visibility**: input, output and cached token counts are stored per question. Questions with no relevant passage never reach the LLM. |
| NFR-08 | **Observability**: structured JSON logs with a request ID on every line, one log line per request and per ingestion, and latency and token usage stored with every question. |
| NFR-09 | **Security**: API key authentication with `Reader` and `Editor` roles, compared in constant time. The OpenAI API key is read from the environment, given only to the API container, and never logged. Answers are requested with `store=false`, so OpenAI does not keep them for later retrieval. |
| NFR-10 | **Testability**: chunking, ranking fusion and status rules covered by unit tests; ingestion and the question flow covered by integration tests against real PostgreSQL with pgvector (Testcontainers). The LLM and embedding model are replaced by fakes in tests. |
| NFR-11 | **Local setup**: the whole system, including the embedding model, runs with `docker compose up`. Only an OpenAI API key is needed from outside, and only for generated answers: upload, ingestion and search work without it. |

## 6. Out of scope

- Scanned PDFs and images (OCR), Word, Excel and PowerPoint files.
- Per-document permissions inside a collection. Access is per role, not per file.
- Web crawling or syncing from Google Drive, Confluence or SharePoint.
- Fine-tuning or training any model.
- Agentic multi-step search with tool calls. One retrieval per question keeps latency and cost predictable.
- Multi-tenant hosting and horizontal scaling of the vector store.

## 7. Glossary

| Term | Meaning |
|---|---|
| RAG | Retrieval-Augmented Generation: retrieve relevant text first, then let an LLM answer from it. |
| Chunking | Splitting a document into passages small enough to embed and retrieve precisely. |
| Embedding | A fixed-length vector representing the meaning of a text. |
| Cosine distance | The measure of how far apart two embeddings are; smaller means more similar. |
| HNSW | The approximate nearest-neighbour index pgvector uses to search vectors quickly. |
| Hybrid search | Combining vector search with keyword (full-text) search. |
| RRF | Reciprocal Rank Fusion: merging ranked lists by summing `1 / (k + rank)` for each item. |
| Hit rate@k | Share of evaluation questions where a correct source passage appears in the top k results. |
| MRR | Mean Reciprocal Rank: average of `1 / rank` of the first correct passage. |
| Faithfulness | Whether every claim in the answer is supported by the cited passages. |

## 8. Decisions taken

These defaults were chosen to keep scope realistic.

| Decision | Choice | Reason |
|---|---|---|
| Language | Python 3.13 with FastAPI | The RAG and evaluation ecosystem is Python-first, and it is what AI engineering roles ask for. |
| Answer model | OpenAI `gpt-5.4-mini` (configurable) through the official `openai` SDK and the Responses API, streamed | Cheap and fast enough for short grounded answers. Citations come from `[n]` markers the model is told to write, parsed and checked against the numbered sources. |
| Embedding model | `nomic-embed-text` served by Ollama in Docker | Runs locally for free, 768 dimensions, good retrieval quality for its size. |
| Vector store | PostgreSQL with pgvector | One database for documents, chunks, vectors, full-text search and jobs. A dedicated vector database is not needed at this size. |
| Ingestion queue | The `documents` table itself, polled with `SELECT ... FOR UPDATE SKIP LOCKED` | Reliable and transactional without adding a message broker or a second table to keep in sync. |
| Retrieval | Hybrid (vector + full-text) with RRF, top 6 chunks | Vector search misses exact terms like policy codes; keyword search misses paraphrases. Together they cover both. |
| Chunking | Split by headings and paragraphs, at most 300 words (about 400 tokens) with a 45-word overlap | Keeps chunks on one topic and keeps the page or heading for citations. Counting words instead of tokens avoids shipping a tokenizer for a limit that only needs to be approximate. |
| Reranking | Could-have, added only if evaluation shows retrieval is the weak point | Adds latency and a model to host; measure first. |
| Auth | Static API keys mapped to roles | Enough to show role checks without building an identity server. |
